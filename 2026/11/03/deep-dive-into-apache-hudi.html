Deep Dive into Apache Hudi

History, architecture, performance optimizations and limitations of Apache Hudi

Date: November 3, 2026  |  Estimated Reading Time: 22 min  |  Author: Neha Thakur
Table of Contents

    History

    Apache Hudi (Hadoop Upserts Deletes and Incrementals) was built at Uber around 2016. Because of the scale of data for real-time ingestion and ETL pipelines, they were looking for something that could provide ACID transactions on top of immutable data files, while the data itself was always mutating. So they built Hudi, which was later open-sourced in 2017 and donated to the Apache Software Foundation in 2019.

    At its core, Hudi wanted to connect relational databases to object storage, such as a data lake where massive amounts of structured and semi-structured data are stored. It wanted a way to connect these both together through change data capture (CDC), where every insert, update and delete in the database is streamed and applied to the data lake. That’s the reason why record-level indexing and merge-on-read are at Hudi’s core.

    Record Keys and Indexing

    Every row in a Hudi table has a unique record key, stored in the data file in a metadata column (_hoodie_record_key), and this hoodie key is a combination of record key (like a primary key) + optionally partition path. The record key comes from the upstream apps like relational databases or any other upstream app that generates a unique ID (e.g. a primary key or UUID). Hudi’s index maps each record key to the file group it’s stored in, so when an update arrives, Hudi knows exactly which file it belongs to.

    Indexing is at the core of Hudi. With indexing, Hudi avoids scanning the entire tables for CRUD operations (mainly updates and deletes, as the index is used by writers to find which file group an incoming record belongs to) thereby speeding up the performance. For eg: If we need to update the email ID of the user_12345, with indexing Hudi will be able to locate in which file this user is located.

    Types of Indexes

    The type of index you would use with Hudi varies based on use case, data volume, update frequency and access patterns:

    Bloom Index

    Every data file contains a tiny, smart checklist of keys inside it. Hudi checks this checklist first and if a record is not in the file, Hudi skips this file. This checklist is a Bloom filter stored in the footer of each base Parquet file (and optionally in the metadata table), along with the min/max key range of the file. A Bloom filter can only say “definitely not here” or “maybe here”, so the files that say “maybe” still have to be opened to confirm. It works best when keys are roughly ordered (e.g. prefixed with a timestamp) and updates mostly hit recent data.

    Simple Index

    It takes the incoming batch of updates and runs a table JOIN against the keys of existing data files. For every write, Hudi reads the record key column from all the base files in the partitions being written to and joins it with the incoming batch, so the cost grows with the size of the partitions, not the size of your batch. Updating 10 rows in a partition with 1 billion rows still means reading 1 billion keys. This is fine for small tables, or when updates are spread randomly across files, but gets slow and expensive on large datasets. It’s the default index for Spark writes in recent Hudi versions.

    Record Index

    Hudi stores an ultra fast key-value pair in its metadata store (the metadata table at .hoodie/metadata/ under the table’s base path, in a partition called record_index, stored as HFiles, a sorted key-value file format built for fast single-key lookups) and looks up for information to find a specific record. The key is the record (primary) key and the value is the record’s location (partition path + file group ID), not the whole row, so the index stays small. It’s a global index, meaning keys are unique across the whole table, not just within a partition.

    Bucket Index

    Bucket Index calculates mathematical hashing on the primary key (such as userid_12345 always hashes to bucket no.4) When Hudi writes/reads it just does the math to calculate the hash to determine the file this userid_12345 is located at. If the information about userId_12345 changes (e.g. their email), nothing needs to be recalculated: the hash is calculated on the record key, not the row’s values, so userId_12345 always hashes to the same bucket and the update goes to that bucket’s file group. The bucket index isn’t stored anywhere either; Hudi just recalculates hash(key) % number_of_buckets on every write, and each bucket maps to one file group whose file ID starts with the bucket number (e.g. 00000004-...). The challenge is that the number of buckets per partition is set when the table is created and can’t easily be changed: too few buckets make files grow very large, and too many create small files. The consistent hashing bucket index (for merge-on-read tables) solves this by resizing buckets over time.

    HBase Index

    HBase Index is when Hudi outsources the entire indexing operation to an external database (Apache HBase), when Hudi needs to locate a record, it just asks HBase. This means running and maintaining a separate HBase cluster, so since the record index was introduced in Hudi 0.14, it’s rarely chosen for new tables.

    In-memory Index

    It is locating the index inside of Hudi’s RAM (in-memory), this is purely temporary and once the job finishes the index is gone. It’s mainly used for testing and small jobs, because the index has to be rebuilt every time.

    Global vs Non-global Indexes

    Bloom and Simple indexes also come in global variants (GLOBAL_BLOOM, GLOBAL_SIMPLE). A non-global index only makes keys unique within a partition, so Hudi only checks the incoming record’s partition. A global index makes keys unique across the whole table, which matters when a record can move partitions, for example when a user moves from country=UK to country=US.

    Index Stored where Best for Watch out for
    Bloom Parquet footers / metadata table Ordered keys, updates to recent data False positives with random keys
    Simple Nothing (joins against data files) Small tables, random updates Cost grows with partition size

    Architecture

    Let’s follow one change end to end: user_12345 updates their email.

    1. Source database: The app runs UPDATE users SET email = 'new@mail.com' WHERE user_id = 12345;. Every database writes each change to its own transaction log before committing it (the binlog in MySQL, the WAL in PostgreSQL), and this log is what makes CDC possible.
    2. Debezium (CDC): Debezium reads the transaction log, not the tables, so it puts almost no load on the database. It turns each change into an event with the operation (c for insert, u for update, d for delete), the row before and after the change, and a timestamp: 
      { "op": "u",
  "before": { "user_id": 12345, "email": "old@mail.com" },
  "after":  { "user_id": 12345, "email": "new@mail.com" },
  "ts_ms": 1762160000000 }
    3. Kafka topic: The events are published to a topic per table (e.g. shop.users), keyed by the primary key, so all the changes for user_12345 stay in order. Kafka also buffers the events, so if Hudi is slow or down, nothing is lost.
    4. Hudi writer: Hudi Streamer, Spark or Flink consumes the events in batches. For each batch, it takes the after row and uses user_id as the record key, keeps only the latest change per key using an ordering field (ts_ms), turns d events into deletes, looks up the index to find the file group, writes the update (a new file slice for copy-on-write, a log file for merge-on-read) and commits to the timeline. Hudi Streamer also stores the Kafka offsets it processed in the commit, so after a crash it resumes from exactly the right spot without duplicates.
    5. Meta sync to Glue: After the commit, the writer syncs the table’s schema and partitions to Glue Data Catalog, so Athena can see new columns and partitions. Unlike Iceberg, where the catalog holds the pointer to the latest commit, Glue only holds the table definition and base path; the timeline in S3 is the source of truth.
    6. Query engines: Athena, Trino or Spark look up the table in Glue, read the timeline to find the latest completed commit and its file slices, and read those files. A few minutes after the app ran the UPDATE, a query on the data lake returns new@mail.com.

    Layer by layer, this is how Hudi stores the files. Firstly, the user decides how they want to partition the files, for example on country, date or day etc.

    • Base path: the root folder of the table.
    • Partition path: for example, country=US one path, country=UK one path, country=France one path.
    • File groups: each partition has file groups, each identified by a file ID. A record key always belongs to one file group.
    • File slices: each file group can have multiple file slices. Each slice is a version of the file group: a base Parquet file plus, in merge-on-read, log files with the changes made after it.

    When the data keeps streaming, the Parquet files themselves never change. In copy-on-write, an update rewrites the base file as a new file slice. In merge-on-read, updates are appended to log files in the current file slice, and compaction later merges them into a new base Parquet file. New inserts can also create new file groups.

    Table Types: Copy-on-Write vs Merge-on-Read

    You choose the table type when you create the table, and it decides how Hudi writes changes to the data and how users or engines read the data:

    Copy-on-Write (CoW)

    When the changes are made to data, such as updating a row, etc. Hudi writes a new version of the file, containing the old rows along with the updated changes. Old files stay until a cleaner job is run. This is good for when the tables need to be read heavy, because all the work happens at write time. Every file is already a complete, up-to-date Parquet file, so readers just read it, with nothing to merge at query time. If a table is written once an hour but queried thousands of times, it’s better to pay the cost once during the write than on every read.

    Merge-on-Read (MoR)

    In these table types, when data is changed, Hudi appends the changes to a small log file (Avro) next to the base file, and when a reader (query engine) reads the data, the base file and the log files are merged at query time. A compaction job later merges the log files into a new base Parquet file, so the logs don’t keep growing. This is good for write heavy workloads, because a write only appends the changed rows to a small log file, instead of rewriting a whole Parquet file (up to ~120 MB) for every update. This makes writes fast and cheap, so data can land in the lake within minutes, which is perfect for streaming and CDC. The cost moves to read time, when the logs have to be merged, and to compaction.

      Copy-on-Write Merge-on-Read
    Update cost High (rewrites the whole file) Low (appends to a log file)
    Read cost Low (Parquet only) Higher (merges base + logs) until compaction
    Data freshness Slower Faster
    Compaction needed No Yes
    Best for Read-heavy, batch updates Write-heavy, streaming/CDC

    Timeline

    To track the changed data, Hudi has something called the timeline (stored in the .hoodie/ folder at the base path), this is similar to the commits in _delta_log in Delta Lake and the snapshots in metadata.json in Apache Iceberg. For every change in a Hudi table, like a commit, compaction, clean or rollback, it records the action with its time and state (requested → inflight → completed). When an engine comes to read, it first looks at the timeline to find the latest completed commits, and from there which file slices are valid, then reads those files (merging the base and log files for merge-on-read).

    What’s inside .hoodie/?

    The .hoodie/ folder holds the timeline along with the rest of the table’s metadata. A simplified view of what it looks like (in Hudi 1.x):

    s3://my-bucket/hudi/orders/.hoodie/
├── hoodie.properties        ← table config: name, table type (COW/MOR), record key,
│                              partition field, ordering field, table version
├── timeline/                ← the timeline: one file per action and state, e.g.
│   ├── 20261103100000.deltacommit.requested
│   ├── 20261103100000.deltacommit.inflight
│   ├── 20261103100000_20261103100012.deltacommit   (completed)
│   └── history/             ← older instants archived to keep the timeline small
├── metadata/                ← the metadata table (itself a Hudi table, with its own .hoodie/)
│   └── files/  column_stats/  bloom_filters/  record_index/
└── .temp/                   ← marker files for in-progress writes, used to roll back failed writes

    In Hudi 0.x, the instant files sit directly inside .hoodie/, and archived instants go to .hoodie/archived/.

    Metadata Table

    Finding the files of a table by listing folders in S3 is slow, since S3 returns at most 1,000 files per list call, and this gets worse as the table grows. To avoid this, Hudi keeps a metadata table inside .hoodie/metadata/. It’s an internal Hudi table (merge-on-read, with HFiles as base files) that is updated in the same commit as your data, so it never goes out of sync. It’s split into partitions, each one storing a different kind of index:

    • files: the list of files in every partition, so readers and writers never have to list S3.
    • column_stats: min/max values and null counts of the columns for every file, used for data skipping.
    • bloom_filters: the Bloom filters of every base file, so the Bloom index doesn’t have to open each Parquet footer.
    • record_index: the record index we covered earlier.

    For example, the files partition stores one key-value record per partition, plus one record listing all the partitions:

    key: "__all_partitions__"  →  [country=US, country=UK, country=France]
key: "country=UK"          →  [fg-1_t1.parquet, .fg-1_t1.log.1, .fg-1_t1.log.2, fg-1_t4.parquet, fg-2_t2.parquet]
key: "country=US"          →  [...]

    So to find the files in country=UK, Hudi does a single key lookup instead of listing the S3 folder. The listing includes every committed file that still exists, including older file slices the cleaner hasn’t removed yet (like fg-1_t1.parquet and its log files above), and the reader then uses the timeline to pick the latest valid file slice in each file group (fg-1_t4.parquet and fg-2_t2.parquet). Since the metadata table is itself a merge-on-read table, every commit appends the files it added or removed as small log records, which are later compacted into its HFiles.

    The metadata table plays a similar role to the manifest files in Iceberg and the _delta_log in Delta Lake: the engine reads metadata instead of scanning storage.

    How does this compare to Delta Lake and Iceberg?

    Hudi splits its metadata into two parts: the timeline is the transaction log (the source of truth for what’s committed), and the metadata table is an optional index that makes finding files faster. Delta Lake keeps both in one place, since _delta_log stores the commits along with the files added and removed, while Iceberg splits them into metadata.json and the manifest files:

    Role Hudi Delta Lake Iceberg
    Table config + schema hoodie.properties + schema in commit metadata metaData entries in _delta_log metadata.json
    Commit history (source of truth) Timeline JSON commits in _delta_log Snapshots in metadata.json
    File list + stats (for speed) Metadata table add/remove entries + checkpoint Parquet Manifest list + manifests
    Catalog Glue / Hive Metastore (via meta sync) Glue / Hive Metastore / Unity Catalog Glue / Polaris / REST (holds the commit pointer)

    Note that .hoodie/ is not the catalog. It lives with the data in S3, while the catalog (Glue) only maps the table name to its schema and base path. Unlike Iceberg, where a commit is the catalog’s pointer swap, Hudi (like Delta Lake) commits in storage, on the timeline.

    Query Types

    Hudi supports different ways of reading the same table:

    • Snapshot query: returns the latest committed data. For copy-on-write, this just reads the latest base files. For merge-on-read, it merges the base files with their log files at query time, so you get the freshest data but pay the merge cost.
    • Read-optimized query: only for merge-on-read. It reads only the base files and skips the log files, so it’s as fast as copy-on-write, but it only shows the data as of the last compaction.
    • Incremental query: returns only the rows that changed after a given commit time. Instead of reprocessing the whole table, a downstream ETL job can just pick up what changed since its last run. Hudi had this from the start, while Delta Lake (Change Data Feed) and Iceberg (incremental reads) added similar features later.
    • Time travel: reads the table as it was at a past commit.
    # Incremental query in Spark: only rows changed after this commit time
(spark.read.format("hudi")
  .option("hoodie.datasource.query.type", "incremental")
  .option("hoodie.datasource.read.begin.instanttime", "20261103100000")
  .load("s3://my-bucket/hudi/orders/"))

    When a merge-on-read table is synced to Glue, it shows up as two tables: orders_ro for read-optimized queries and orders_rt for snapshot (real-time) queries.

    Key Features

    Just like any other OTF, Apache Hudi also provides ACID transactions, time travelling (data versioning), schema evolution and concurrency control. On top of these, it’s built around record-level upserts and deletes using record keys, and incremental processing (incremental and CDC queries), which is what makes it a good fit for streaming and CDC pipelines.

    Performance

    Indexing

    Every time a batch of changes arrives, Hudi first tags each incoming record: it uses the index to find out whether the record key already exists, and if so, in which file group. Updates are then routed straight to their file groups and new records are treated as inserts. Without an index, Hudi would have to compare the incoming keys against every key in the table to know which files to change. With an index, only the file groups that actually contain the changed records are touched, so the cost of a write depends on how much data changed. Choosing the right index type (see the table above) is one of the most important performance decisions in Hudi.

    MVCC and Concurrency Control

    Hudi uses Multi-Version Concurrency Control (MVCC): instead of locking files, it keeps multiple versions of each file group (file slices). A reader always reads the file slices of the latest completed commit on the timeline, while a writer creates new file slices or log files that readers only see once the commit is completed. This means readers always get a consistent snapshot, and a writer and table services like compaction and cleaning can run at the same time as readers, without any locks.

    For multiple writers writing to the same table, Hudi uses Optimistic Concurrency Control (OCC), just like Iceberg and Delta Lake, but with one big difference from Iceberg: Hudi needs an external lock provider, such as DynamoDB, ZooKeeper or Hive Metastore, to make sure only one writer commits at a time. At commit time, Hudi checks whether another writer committed changes to the same file groups in the meantime. If not, both commits succeed; if they did, the later commit fails and has to be retried.

    As we saw in the Iceberg post, OCC struggles when many writers constantly update the same data. To solve this, Hudi 1.0 introduced Non-Blocking Concurrency Control (NBCC) for merge-on-read tables (only works with MoR tables): multiple writers can write to the same file groups at the same time without failing each other, since each writer only appends to its own log files. The conflicts are resolved later, when the files are merged during reads or compaction, using the ordering field (for example the event time) to decide which version of a record wins.

    Table Services

    Hudi comes with built-in table services that keep the table healthy and fast. They are scheduled and recorded on the timeline just like commits.

    • Compaction (merge-on-read only): merges the log files of a file slice into a new base Parquet file, so readers have less to merge. It can run inline, right after a write (for example every 5 delta commits), which is simple but slows down the writer, or async, in a separate job or alongside a streaming job, so the writer keeps writing.
    • Cleaning: removes old file slices that are no longer needed, similar to snapshot expiry in Iceberg and VACUUM in Delta Lake. By default, Hudi keeps the file slices needed for the last 10 commits, and you can instead keep a number of file versions or a number of hours. Once a file slice is cleaned, you can no longer time travel to it (obviously!).
    • Clustering: rewrites data files to sort the data by the columns you query most (linear sorting, Z-order or Hilbert curves) and merges small files into bigger ones, similar to Z-ordering in Delta Lake and sort compaction in Iceberg. Since clustering moves records to new file groups, it shows up on the timeline as a replacecommit.
    • Automatic file sizing: Hudi tries to avoid the small file problem in the first place. When new records are inserted, Hudi routes them into existing files smaller than ~100 MB until they reach ~120 MB, instead of always creating new small files. But with MoR the log files still pile up until compaction function merges them.

    Data Skipping

    Just like Iceberg’s manifest files, Hudi can skip files that can’t contain the data you’re filtering on. The column_stats partition of the metadata table stores the min/max values of the columns for every file, and when data skipping is enabled, the query engine checks these stats first and only reads the files whose range matches your WHERE clause. This works best when the data is sorted or clustered on the columns you filter on.

    Note that Hudi doesn’t have hidden partitioning like Iceberg: partition pruning only works when your query filters on the partition column itself. In Hudi 1.0, expression indexes can help with this by indexing an expression on a column (e.g. the date part of a timestamp), so queries filtering on the timestamp can still skip files.

    Limitations

    • Complexity: Hudi has a lot of configurations (table types, index types, table services, concurrency modes), and choosing and tuning them for your workload takes time and experience.
    • Copy-on-write vs merge-on-read tradeoff: Copy-on-write rewrites whole files for small updates, making writes expensive, while merge-on-read makes reads slower until compaction runs, and compaction itself needs to be scheduled and monitored.
    • Multiple writers need extra infrastructure: Unlike Iceberg, where the catalog decides which commit wins, Hudi needs an external lock provider like DynamoDB or ZooKeeper for concurrent writers.
    • Narrower engine support: Spark and Flink have the best support. Other engines often only support reads, for example Amazon Athena can query Hudi tables but can’t write to them.
    • Record keys: Hudi has traditionally required a record key for every table, which doesn’t always fit append-only data like logs. Newer versions can auto-generate record keys.
    • No hidden partitioning: Partitioning is based on a column you provide, and changing how a table is partitioned means rewriting the data.
