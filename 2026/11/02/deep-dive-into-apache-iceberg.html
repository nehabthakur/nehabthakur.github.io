Deep Dive into Apache Iceberg

History, architecture and key features of Apache Iceberg

Date: November 2, 2026  |  Estimated Reading Time: 17 min  |  Author: Neha Thakur
Table of Contents

    In this post, we’ll dive deep into Apache Iceberg.

    History

    Apache Iceberg was created at Netflix around 2017 by Ryan Blue and Dan Weeks, open-sourced and donated to the Apache Software Foundation in 2018. Before Apache Iceberg, the industry widely used Apache Hive as a table format and metadata layer. Hive tracked data at the folder/directory level, which introduced severe performance and ACID compliance challenges. Although Apache Hive introduced ACID compliance in its 0.13 version (around 2014), it suffered from critical bottlenecks because data tracking remained tied to the folder level:

    • If a user or an execution engine like Spark needed to find, read, or change data within a particular file, it had to scan all the files inside that folder partition. Because Hive tracked data at the folder level, it could not pinpoint a specific file path directly. It first had to list every file in the folder, which is slow on object stores like S3, and since Hive kept no per-file statistics (like min/max values), it couldn’t skip files that didn’t contain the data it needed. Imagine you have a box (folder) containing 50 books (files); to find a book titled “abc”, you have to dig through the entire box because there is no catalog telling you exactly where that book sits.
    • To provide ACID transactions, Hive relied on a relational database (like MySQL) to place a lock on the entire table or partition during a write operation. This drastically limited concurrent writes; other writers were forced to wait in a queue, frequently leading to performance timeouts.
    • Hive did not maintain an explicit, deterministic ledger of file changes. Instead, changes generated a chaotic trail of small delta subfolders. Because the metastore tracked transaction IDs, but not which files belonged to which version, background garbage collection and compaction routines had to heavily scan the physical storage layout, causing severe performance degradation.

    A Quick History about Hive

    Hive was built at Meta (Facebook) to query massive amounts of data. The underlying data was stored on HDFS (Hadoop Distributed File System). Because querying data directly on HDFS required engineers to write complex, low-level MapReduce Java programs, it was highly inaccessible to business analysts and non-programmers.

    To solve this, the engineers built a middle layer called Hive. Hive allowed users to write familiar SQL-like queries using a dialect called HQL (Hive Query Language). Hive would then automatically take those SQL(HQL) queries, translate them into MapReduce jobs under the hood, and run them against the data hosted on HDFS. Hive was built for on-prem storage devices and completely broke when businesses started moving to cloud object stores like Amazon S3, GCP and Azure ALDS, as these are flat files and not folder level stores.

    I’m going to write about HDFS, MapReduce in my future blogs, so stay tuned.

    Architecture

    Iceberg organizes metadata in a hierarchical, tree-based structure (Catalog -> Metadata File -> Manifest List -> Manifest Files -> Data Files).

    You upload raw files to an S3 bucket -> create a table on top of them in Glue Data Catalog (or can your OSS Apache Polaries) -> then use Athena/Spark/Trino or any engine of your choice to write that data into an Iceberg table, as Parquet (columnar file format) data files. In Athena this is a CTAS query with table_type = 'ICEBERG', which writes the data as Parquet files and, in the same step, creates the metadata files in S3:

    CREATE TABLE reviews_iceberg
WITH (
  table_type = 'ICEBERG',
  format = 'PARQUET',
  location = 's3://my-bucket/iceberg/reviews/'
)
AS SELECT * FROM reviews_raw;

    The catalog (Glue Data Catalog, or any other data catalog like Apache Polaris) doesn’t track the Parquet files. It stores a single pointer to the table’s current metadata.json file. metadata.json is the top layer: it holds the schema, partition spec, and the list of snapshots(what are snapshots?). Below that is a manifest list per snapshot, then manifest files, which point to the actual Parquet files at the bottom and store their partition values and column stats.

    Whenever you make some change to the data, Iceberg creates updated files without overwriting the previous ones. New data files don’t go into an existing manifest, since manifests are immutable too. Each commit writes a new manifest for the files it added, and a new manifest list that points to the old, unchanged manifests plus the new one. Then it writes a new metadata.json with the new snapshot, and the catalog pointer is atomically swapped to it.

    Hidden Partitioning

    We initially define which columns we want to partition the data on, for eg: We might want to partition data on the column country, so that all the rows with country = ‘UK’ are stored together, all the rows with country = ‘US’ are stored together, and so on. But unlike Hive, we don’t need to create or fill in a separate partition column ourselves, Iceberg does it for us, which is why it is called “hidden” partitioning.

    In Hive, if you wanted to partition your data by date, you had to create a separate column (e.g. event_date) derived from your timestamp column and populate it yourself on every write. Readers then had to remember to filter on event_date instead of the timestamp; if they forgot, Hive would scan the entire table. And if someone populated event_date with the wrong format or timezone, the rows would silently land in the wrong partition.

    With Iceberg, you define the partition as a transform(ts) on an existing column:

    CREATE TABLE events (id BIGINT, ts TIMESTAMP, country STRING)
PARTITIONED BY (day(ts), country)
LOCATION 's3://my-bucket/iceberg/events/'
TBLPROPERTIES ('table_type' = 'ICEBERG');

    Now whenever you write data, Iceberg reads the ts value of each row, works out the day, and writes the row into a data file for that partition. When you query, you simply filter on ts:

    SELECT * FROM events
WHERE ts >= TIMESTAMP '2026-11-02 00:00:00'
  AND ts <  TIMESTAMP '2026-11-03 00:00:00';

    Iceberg converts this into a filter on the day partition and skips every file that doesn’t match, using the partition values stored in the manifest files. You never have to know how the table is partitioned to get a fast query.

    Note that you define the transform only once, when you create the table, not in every query, and you never transform the data yourself. Also, “hidden” doesn’t mean Iceberg adds a hidden column to your data. The Parquet files only contain your real columns; the partition value (e.g. ts_day=2026-11-02) is stored in the metadata, in each data file’s entry inside its manifest.

    The transforms Iceberg supports are:

    Transform Example Use case
    identity country Low-cardinality columns
    year / month / day / hour day(ts) Time-series data
    bucket bucket(16, user_id) Spreading high-cardinality keys evenly
    truncate truncate(4, zip_code) Grouping by a prefix of a string or a range of numbers

    What happens when new data arrives?

    A partition isn’t a single file, it’s a group of files that share the same partition value, and every data file holds rows from only one partition. Since data files are immutable, if you add new rows for country = ‘UK’, Iceberg doesn’t append them to the existing UK file. It writes a new data file, tags it country=UK in a new manifest, and commits a new snapshot. Now the UK partition is made up of two files, and when you query WHERE country = 'UK', Iceberg collects every file whose manifest entry says country=UK and skips the rest.

    The same goes for dates. New data for 2026-11-02 doesn’t get added to the manifest that holds the previous 2026-11-02 files, since manifests are immutable too. Each commit writes its own new manifest, so files for the same day can end up spread across several manifests. When you filter on 2026-11-02, Iceberg first uses the ts_day range stored for each manifest in the manifest list to skip the manifests that can’t contain that day, and then, inside the remaining manifests, picks only the files tagged ts_day=2026-11-02:

    Over time, frequent small writes leave many small files in each partition. Compaction (OPTIMIZE ... REWRITE DATA USING BIN_PACK in Athena) reads these small files and writes them out as one bigger file per partition, again as new files, while the old ones stay around for time travel until you expire them.

    Partition Evolution

    Because queries never reference the partition layout directly, you can change how a table is partitioned without rewriting any of the existing data. For example, if your data grows and daily partitions become too big, you can switch to hourly partitions:

    -- Spark SQL (Athena doesn't support partition evolution)
ALTER TABLE events REPLACE PARTITION FIELD days(ts) WITH hours(ts);

    The old data files stay in their daily partitions and new data files are written hourly. Each manifest records which partition spec it was written with, so Iceberg knows how to prune both old and new files in the same query, and none of your queries need to change.

    Key Features

    Just like any other OTF, Apache Iceberg also provides time travelling (data versioning), schema evolution, ACID transactions and concurrency (OCC).

    Side note: Optimistic Concurrency Control (OCC)

    As we saw earlier, Hive used pessimistic locking: it locked the table or partition before a write, and every other writer had to wait in a queue. OCC takes the opposite approach. It assumes conflicts are rare, so writers don’t lock anything; they all work in parallel and only check for conflicts at the very end, when they commit.

    In Iceberg, a write works like this:

    1. The writer reads the current metadata.json (say v1) and treats it as its starting point.
    2. It writes its new data files, manifest, manifest list and a new metadata.json (v2). Nobody else can see these files yet.
    3. It asks the catalog to swap the table pointer from v1 to v2, only if the pointer is still at v1. The catalog does this check and swap as one atomic step.

    If another writer committed first, the pointer has already moved, so the swap fails. The writer then reads the latest metadata and checks whether the other commit actually conflicts with its own (for example, both updated or deleted rows in the same data files). If there’s no conflict, like two writers appending data to different partitions, it reuses the data files it already wrote, regenerates only the metadata files on top of the latest version, and retries the swap. If there is a conflict, the commit fails and the job has to be rerun.

    Imagine two people editing the same Wikipedia page. Neither of them locks the page while they type, but when you hit save, Wikipedia checks whether someone else saved since you started. If they did, you have to reconcile your changes with theirs before your edit goes through.

    This is the same idea as Delta Lake, where the first writer to create the next numbered JSON file in _delta_log wins. In Iceberg, the “winner” is decided by the catalog’s pointer swap instead.

    Note that OCC doesn’t affect reads at all; readers always just follow the catalog pointer to the latest committed snapshot. The challenges come from commits, in two cases:

    • Multiple writers committing at the same time: only one pointer swap can win at a time, so the more writers commit at once, the more of them fail and retry. Retrying an append is cheap, since only the metadata files are regenerated, but with many writers committing frequently, jobs spend more and more time retrying and can fail once they run out of retries.
    • Multiple jobs changing the same data files: for example, an UPDATE/DELETE job and a compaction job both rewriting the same files. Here a retry can’t simply be stacked on top of the other commit, so one of the jobs fails and has to be rerun.

    So how does this work with streaming, where data never stops arriving? Streaming engines continuously write data files, but only commit once in a while. Spark Structured Streaming commits once per micro-batch (e.g. every minute), and Flink has many parallel tasks writing files with a single committer committing them once per checkpoint. So even a job with hundreds of parallel tasks only makes about one commit per minute. The tradeoff is that data only becomes visible to readers after each commit, and frequent commits leave behind lots of small files and snapshots that need regular compaction and snapshot expiry.

    Iceberg works well with a handful of writers committing every few seconds to minutes, but it wasn’t built for many jobs constantly upserting (updating or inserting rows, which means writing new files and committing each time) into the same table. This is exactly the problem Apache Hudi was built for at Uber, where streaming upserts were the main use case. Hudi 1.0 even introduced non-blocking concurrency control, which lets multiple writers write to the same table without failing each other. More on that in my next post on Hudi!

    Performance

    There are a lot of optimizations you can do in terms of reads and writes with Apache Iceberg, some of the important ones are:

    File Pruning

    Because Iceberg tracks every data file in its metadata, a query engine can skip most files without ever opening them. This happens at three levels:

    1. Manifest list: For every manifest, the manifest list stores the range of partition values it covers. Manifests that can’t match your WHERE clause are skipped completely, like manifest C in the hidden partitioning diagram above.
    2. Manifest files: For every data file, the manifest stores its partition value and column statistics, such as the min/max values, null counts and value counts. Iceberg collects these for the first 100 columns by default, and the engine skips every file whose min/max range can’t contain the value you’re filtering on.
    3. Parquet files: Inside the files that are left, Parquet keeps its own min/max statistics per row group, so the engine can skip parts of a file too.

    File pruning on column stats works best when data is sorted. If the rows for a user_id are spread across every file, every file’s min/max range will contain it and nothing gets skipped. You can define a sort order on the table (ALTER TABLE events WRITE ORDERED BY user_id in Spark), so that similar values end up in the same files and the min/max ranges stay tight.

    Compaction

    As we saw earlier, frequent writes leave many small files behind, and with merge-on-read, many delete files that readers have to merge at query time. Compaction rewrites them into fewer, bigger files and applies the delete files, so readers open fewer files:

    -- Athena
OPTIMIZE reviews_iceberg REWRITE DATA USING BIN_PACK;

    Athena only supports bin-packing, which combines small files without changing the order of the rows. In Spark, rewrite_data_files can also sort the data or Z-order it on multiple columns while compacting, just like Z-ordering in Delta Lake:

    -- Spark SQL
CALL glue_catalog.system.rewrite_data_files(
  table => 'amazon_reviews.reviews_iceberg',
  strategy => 'sort',
  sort_order => 'zorder(user_id, asin)'
);

    Similarly, many small commits leave many small manifests, which slows down query planning. rewrite_manifests regroups them into fewer manifests, grouped by partition.

    Snapshot Expiry

    Every commit creates a new snapshot, and the old snapshots keep pointing to data files that are no longer part of the current table, so they can’t be deleted. This is what makes time travel possible, but if you never clean up, your S3 bucket and your metadata keep growing forever. Expiring snapshots removes the old snapshots from the metadata and deletes the data and metadata files that only they referenced:

    -- Athena
VACUUM reviews_iceberg;

    In Athena, VACUUM expires snapshots older than 5 days by default (set by the vacuum_max_snapshot_age_seconds table property) and also deletes orphan files, which are files left behind in S3 by failed writes that no snapshot points to. In Spark, the same is done with expire_snapshots and remove_orphan_files. Just like VACUUM in Delta Lake, once a snapshot is expired, you can no longer time travel to it.

    Limitations

    • Maintenance overhead: Because files are immutable and every commit adds new data and metadata files, an Iceberg table doesn’t stay fast on its own. You need to regularly run compaction, rewrite manifests and expire snapshots, otherwise reads slow down and storage keeps growing. Managed options like AWS Glue Data Catalog’s automatic table optimization and Amazon S3 Tables can run these for you, but at an extra cost.
    • Catalog dependency: Every read and commit goes through the catalog, so every engine that reads or writes a table has to use the same catalog. Catalogs like Glue, Polaris, Nessie or Hive Metastore also support different features, and moving tables from one catalog to another isn’t trivial.
    • Uneven engine support: Iceberg is an open spec, but each engine implements a different part of it. For example, Athena doesn’t support partition evolution and only supports bin-packing for compaction, and newer features from the v3 spec, like deletion vectors, aren’t supported by every engine yet. So what you can do with a table depends on the engine you use.
    • Frequent upserts and concurrent writes: As discussed in the OCC side note, many writers committing at the same time, or jobs constantly updating the same data files, lead to retries and failed commits. Copy-on-write rewrites whole files for small updates, and merge-on-read slows down reads until delete files are compacted.
