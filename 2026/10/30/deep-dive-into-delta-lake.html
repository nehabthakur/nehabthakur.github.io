Deep Dive into Delta Lake

History, architecture, performance optimizations and limitations of Delta Lake

Date: October 30, 2026  |  Estimated Reading Time: 8 min  |  Author: Neha Thakur
Table of Contents

    History

    As you might already know, the creators of Apache Spark founded Databricks, and initially used Spark along with Apache Hive Metastore for their big data processing. However, as I have discussed in my previous post, Apache Hive tracked files strictly at folder/partition level and if you needed to make an update to a single row, you’d have to swap out and rewrite the entire folder. This means it was highly inefficient for writes, and if a write failed halfway through, it would leave partially written files behind that readers would treat as valid data. Furthermore, Spark pipelines running on cloud object storage like Amazon S3 lacked ACID properties, which led to data corruption and partially written data folders when processing jobs crashed.

    To solve this problem, Databricks built Delta Lake around 2017, which introduced a centralised transaction log (_delta_log). It was open-sourced in April 2019 and later that year moved to the Linux Foundation.

    A Quick Recap

    Delta Lake is among the three most popular and most used Open Table Formats (OTFs) used in production today. Like other OTFs, Delta Lake provides ACID compliance, Schema Evolution, Data Versioning, and reduces vendor lock-in.

    Architecture

    Note: The _delta_log file names in the diagram are shortened for readability. Actual commit files are zero-padded to 20 digits (e.g., 00000000000000000000.json).

    Let’s start from the beginning, you land/dump your raw data into an object storage (like S3).

    Using a processing engine, primarily Apache Spark, you write the data out directly as Delta format, which consists of standard Apache Parquet files (a highly compressed, columnar format):

    df.write.format("delta").save("s3://my-bucket/delta-table")

    The moment an engine executes this command, it first writes the Parquet data files and then creates a _delta_log/ folder with a commit that lists them. If the job crashes before the commit, readers never see those files. This directory is now a Delta Table.

    Every time an engine makes changes to this table, Delta Lake makes an entry in the _delta_log/ using sequential, numbered JSON text files (e.g., 00000000000000000000.json, 00000000000000000001.json, 00000000000000000002.json). Each of these entries is called a commit and states exactly which files were added or removed, along with any schema changes.

    A commit only succeeds if the writer is the first one to create the next numbered JSON file. If two writers try to create the same file at the same time, one wins. If the changes don’t conflict, the other writer retries; if they do, it fails. This is how Delta Lake makes sure that concurrent writes don’t step on each other. On S3, writing from multiple clusters historically needed a DynamoDB-backed log store, because S3 couldn’t guarantee that only one writer creates a file.

    When a query engine wants to read the data, it reads these JSON files first to figure out which Parquet files are the latest and valid. Because the number of commits can grow tremendously over time, reading hundreds of JSON files from start to finish would eventually become slow. To prevent this, after every 10 commits, Delta Lake automatically creates a checkpoint Parquet file (e.g., 00000000000000000010.checkpoint.parquet), which captures the full state of the table at that point. A reader can then start from the latest checkpoint and only read the few JSON commits after it.

    Performance

    There are a lot of optimizations you can do in terms of reads and writes with Delta Lake, some of the important ones are:

    Z-Ordering

    Delta Lake colocates rows with similar values in the chosen columns in the same files. Since Delta Lake stores the min/max values of the first 32 columns (by default) for every file in its _delta_log, the engine can skip the files that can’t match your WHERE clause, reducing the amount of data scanned and speeding up queries.

    Delta Lake doesn’t automatically guess which data is related. Instead, you would analyse your most frequent query WHERE clauses and explicitly run an OPTIMIZE command:

    OPTIMIZE my_delta_table ZORDER BY (customer_id, country)

    Delta Lake then uses a mathematical concept called Space-Filling Curve (specifically a Morton Curve / Z-Order curve), where it takes the binary representations of the values in those columns and zips them together like a deck of cards to create a single number (Z-value) for each row, and it then sorts the data by this new Z-value before writing the rows into Parquet.

    Challenges with Z-Ordering

    • Curse of Dimensionality: Z-ordering works well with 2 or 3 columns, but it breaks down when you try to order 5 or 6 columns. If you intertwine two decks of cards (Columns A and B), the pattern is a tight A B A B A B…. But if you intertwine 5 columns, the pattern stretches out to A B C D E A B C D E…. This stretches the rows that share the same value for Column A wildly far apart across files, diluting the sorting effectiveness for each column.
    • Query Pattern Changes: If your business needs change and you need to filter by a brand new column, you have to redo the Z-ordering process from scratch across your historical data.
    • High Write/Compute Costs: Because Z-ordering requires a full sort and isn’t incremental, running it forces your Spark cluster to read, shuffle, and rewrite massive amounts of data from scratch, resulting in heavy compute bills.

    Liquid Clustering: The Successor to Z-Ordering

    Liquid Clustering replaces the rigid bit-math of Z-Ordering with a fluid spatial clustering algorithm (built on Hilbert curves). When new data arrives, Liquid Clustering doesn’t sort the whole historical table. Instead, it writes the new data quickly into separate files in your object storage. When you trigger an OPTIMIZE command, it uses the Hilbert curve algorithm to cluster only the data that isn’t clustered yet, leaving the already clustered files alone. This makes ordering significantly faster and cheaper. Because of the spatial curve design, it can cluster by up to 4 columns with better data skipping than Z-ordering on the same columns.

    And if your query patterns change, you can simply change the clustering columns without rewriting your existing data:

    ALTER TABLE my_delta_table CLUSTER BY (customer_id, order_date)

    The existing data keeps its old clustering until later OPTIMIZE runs re-cluster it with the new columns.

    Liquid Clustering replaces both partitioning and Z-Ordering, so it can’t be combined with either of them. It started on Databricks and is now available in open-source Delta Lake 3.x.

    Compaction of Files

    In streaming or high-frequency batch workloads, data is often written into S3 in small, fragmented files. This causes massive metadata read overhead. Query engines perform far better on fewer, larger files, and Delta Lake has a default target file size of 1 GB for OPTIMIZE (which is fully adjustable; on Databricks it is tuned automatically based on table size).

    To fix this, you run an OPTIMIZE command (without ZORDER):

    OPTIMIZE my_delta_table

    Delta Lake reads its transaction log to check for Parquet data files that are significantly smaller than the target size. The Spark engine reads these tiny files into cluster memory, brings them together logically, and merges them into one or more files of around 1 GB. Delta Lake then writes a new JSON file to the _delta_log/ to commit this update, marking the old small files as removed.

    Limitations

    • Storage Bloat: Because Delta Lake guarantees ACID compliance and Time Travel, it never deletes or overwrites an old file during a compaction or an update. It simply flags it as removed in the log. This causes massive file accumulation and storage bloat in your S3 bucket, meaning you must regularly monitor and run a VACUUM command to physically purge old files. By default, VACUUM keeps files from the last 7 days, and once old files are purged, you can no longer time travel to the versions that used them.
    • Tied to Databricks and Spark: As Delta Lake is tightly woven and heavily optimized for Databricks and Spark runtimes, non-Spark engines like Presto, Trino and Amazon Athena historically struggled to read Delta tables natively, requiring external symlink manifest files to understand which Parquet files were active. Today, Trino and Amazon Athena can read Delta tables natively. Delta Lake has also introduced Universal Format (UniForm), which writes Iceberg metadata alongside the Delta log so other engines can read Delta tables as if they were Apache Iceberg tables. But these engines only get read access, and you still need a catalog like Unity Catalog to expose that metadata, adding to architectural complexity.
