Evolution of Data Storage Layers

Data Warehouse vs Data Lake vs Data Lakehouse

Date: October 29, 2026  |  Estimated Reading Time: 8 min  |  Author: Neha Thakur
Table of Contents

    In the Data Engineering Lifecycle, Data Storage Layer spans across all the other layers and hence is a backbone of your entire data architecture. And the data can be stored anywhere from databases, data warehouses, data lakes. But how these systems handle data is vastly different and the storage option you select depends on the business use case and how the downstream app consumes them.

    Databases

    This is one of the most familiar topics and hence we will not go into depth. As we know, for different needs we have different databases. Some of the most popular ones are Relational databases (Postgres, MySQL, Amazon Aurora), Document DBs, Wide-Column DBs, Graph DBs, and Key-Value DBs, etc. Storing data into these DBs is primarily for OLTP (Online Transaction Processing) purposes. They do not serve well for analytical workloads (OLAP) such as calculating trends or aggregations across millions of records. Because the data in these transactional databases is mostly stored in rows on the disk, the engine is forced to scan a massive amount of unnecessary data just to extract and compute a single metric, taking significantly more time than the specialized analytical options we’ll see below.

    Data Warehouse

    A Data Warehouse is an excellent option for analytical workloads. This is where you dump all of your structured data that has been generated from sources such as:

    • Transactional Systems: Relational databases like PostgreSQL, MySQL, or Amazon Aurora.
    • SaaS Applications: Structured data exported from tools like Salesforce, HubSpot, or Stripe.
    • Logging Systems: Application or system logs that follow a strict, predefined schema.

    Because it stores structured data and enforces schema-on-write, it is ideal for downstream systems like BI tools for report generation and dashboarding.

    Under the hood, data warehouses use columnar storage. While traditional databases read data row-by-row (making them slow for analytical calculations), data warehouses store data column-by-column. If a dashboard only needs to calculate total revenue, the engine skips all other columns on the disk and reads only the revenue data, making analytics extremely fast.

    However, there are challenges with Data Warehouses:

    • Rigid Structure: Data must be structured into rows and columns before entry. Modern warehouses can handle semi-structured JSON (e.g., Snowflake VARIANT, Redshift SUPER, BigQuery JSON), but they cannot natively store raw, unstructured data like videos, audio, or images.
    • The Ingestion Bottleneck: Transforming and cleaning massive volumes of high-velocity, real-time data before writing it to the warehouse can easily lag or bottleneck your data pipeline.
    • Loss of Granular History: Because data must be aggregated or transformed to fit the warehouse schema, you often need to throw away the original, raw data that a data scientist or ML engineer might need for machine learning years down the line. However, sometimes companies might not throw away the raw data but instead store it somewhere, this maintenance of data at multiple places creates complexity.

    Data Lake

    Because of the above challenges of Data Warehouses, Data Lakes were invented. Data Lakes act as a centralised repository and let you store data in its raw, native format without needing to structure it first unlike Data Warehouses, as they follow schema-on-read. They are very cheap and separate storage from compute, letting any engine read the data. They are also extremely flexible in the types of data that can be stored:

    • Structured Data: Tabular rows and columns.
    • Semi-Structured Data: JSON payloads, XML files, and CSVs.
    • Unstructured Data: PDFs, text documents, emails, videos, and audio recordings.

    Despite their flexibility, Data Lakes are bad for traditional business reporting and dashboarding, as they are not indexed and don’t follow ACID compliance and the reporting/dashboarding requires fast, clean SQL tables.

    This meant companies needed to maintain 2 types of data storage systems for analytics. Data warehouses with structured data for reporting/dashboarding and data lakes with all types of data for Machine Learning. Maintaining this is expensive, time consuming and operationally painful. Data Engineers will need to constantly write complex pipelines to sync and move data back and forth between these storage systems. And as I mentioned above, Data Lakes don’t comply with ACID, concurrent writers could corrupt data mid-write and there was no dependable way to know which files represented a table’s current, accurate state.

    Data Lakehouse

    Because of the need to maintain 2 different storage systems, Data Lakehouse was born. To oversimplify it, it is a mix between a Data Warehouse and a Data Lake, meaning you can store all kinds and types of information into your Data Lakehouse, and it will have a magic metadata layer that turns the files in your lake into reliable tables to let you query them with SQL for reporting, all while preserving the raw data underneath for Data Science & ML.

    Magic Metadata Layer

    Spoiler alert, there is no magic here. In reality, a Data Lakehouse adds a metadata layer, called an Open Table Format, on top of columnar files (such as Parquet) in the lake. Raw semi-structured data is first parsed into columns by an engine like Spark, and the Open Table Format then tracks exactly which files make up a table at any point in time. This is what gives plain files on object storage warehouse-like guarantees: ACID transactions, time travel, and schema evolution. Unstructured data like videos and PDFs stays raw in the lake. It gets the name “Open” because the table specifications are completely public i.e., any query engine can read them without being locked into a single proprietary database vendor.

    While there are three popular open table formats used in production today, they all keep a metadata layer that records which data files belong to the table (a file-level index that maps out where data lives). However, how they organize and manage this metadata under the hood is different:

    • Apache Iceberg: Organizes metadata in a hierarchical, tree-based structure (Metadata File -> Manifest Lists -> Manifest Files), with column statistics stored in the manifests so engines can skip unneeded files without opening them.
    • Delta Lake: Open-sourced by Databricks, it uses a transaction log approach (_delta_log/, an ordered ledger of JSON commits with periodic Parquet checkpoints) to track table history and updates.
    • Apache Hudi: Originally created by Uber, it uses a timeline (.hoodie/) of actions on the table and specializes in streaming workloads and low-latency incremental updates, organizing files to handle rapid upserts and deletes.

    Side Note: Before the above table formats, the industry relied heavily on Apache Hive tables. Hive mapped a table name to a directory in the Data Lake and applied a schema to the files at read time. Because Hive didn’t track data at a file-level but rather at a folder-level (whatever files were in the folder were the table), if we needed to update a single row in a file, we would need to re-write the whole folder (partition) again. Hive 3 did later add ACID tables, but in practice most data lakes used plain, non-ACID Hive tables. Think of it like a folder containing 50 physical pages of text. If you want to change just one sentence on Page 42, Hive forces you to modify Page 42 and then re-write all 50 pages completely from scratch because it treats the folder as an inseparable bundle.

    In contrast, modern open table formats use their metadata layer to provide file-level tracking. Data files are immutable and never edited in place, so if you need to make a change on Page 42, the engine writes a new version of only that 1 page (Page 42) and commits it atomically. Because the metadata already lists every file in the table, engines also no longer need to slowly list folders to find the data. Under the hood, this precision is handled using one of two concepts:

    Copy-on-Write

    The engine takes the original page_42_v1, reads it into memory, applies your update, and writes a brand-new page_42_v2 to your storage bucket. The old file is left completely untouched, and the commit creates a new snapshot of the table that references page_42_v2. The previous snapshot still references page_42_v1, which is what makes time travel possible.

    Merge-on-Read

    Instead of rewriting any major data files, this method keeps the original page_42_v1 completely as it is. It writes a separate, lightweight file containing only the specific delta (the update/delete action), such as delete files in Iceberg, deletion vectors in Delta Lake, or log files in Hudi. When you query or read the data through an engine like Apache Spark or Amazon Athena, the engine pulls both the old file and the tiny delta file simultaneously, merging them in memory on the fly to show you the updated data. The trade-off is that writes become fast but reads get slower as delta files pile up, so a periodic compaction job folds them back into the data files.
